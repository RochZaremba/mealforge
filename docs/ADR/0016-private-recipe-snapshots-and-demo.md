# ADR-0016: private recipe snapshots and explicit separate demo

Status: Accepted for W01-C, 2026-10-10. Extends ADR0003/0005/0012/0014. No new framework, dependency or network adapter.

The first private catalogue stores a tenant-scoped recipe identity and immutable typed version snapshots in PostgreSQL JSONB. Literal ingredient amounts are nullable bounded Decimal strings (or validated integer input), with original units and raw/cooked/as_packaged/unknown state. No implicit conversion, nutrient data, allergen safety, cooked yield, timing, price or storage claim is inferred. Every version remains draft_requires_review and planner_eligible=false until future verified nutrition/allergen gates. Instructions render as escaped text, never HTML.

All reads/mutations use current household membership/access authorization. Create/edit require editor/owner, CSRF and idempotency. Updates append an immutable version under expected_version; version rows reject UPDATE/DELETE. A deferred composite current-version FK enforces same-household identity and revision consistency at commit. Audit carries metadata; concurrent writes commit once or return409. Lists return bounded summaries and history at most5full snapshots per page, with reachable pagination and the existing16KiB request/262KiB response budgets.

Provenance is server-controlled. Own submissions explicitly attest i_am_author for the user's contribution, have private_user_content rights and unknown license. Trusted original fixtures are authored by MealForge, CC0-1.0 only for original_recipe_text. Editing preserves immutable original attribution/license and server-side source-version lineage; new user contribution is private/unknown license, never automatically CC0. No external URL/asset/fetch or user-provided validation/license override is accepted. The original fixture is shipped with the installed API package/Docker and checked against the repository fixture; absence/drift must fail demo creation rather than succeed empty. Declared servings2 are recipe design, not measured yield or calorie portions.

POST households/demo requires explicit create_separate_demo confirmation and creates a new owned household, two resident profiles with2700/1600sample targets and null macros, five slots and three original drafts atomically. Household source is persisted user_created|demo_seed; target source user_set|demo_seed and a demo warning are exposed. No real household or targets are altered, no seed occurs on registration/startup. Idempotent demo replay reauthorizes current owner access. Any authenticated account may create its own demo, including a viewer in another household.

Frontend shares selected household ID in auth-scoped ephemeral memory across Today/Household/Recipes; it validates against server list, clears on auth/revocation, and never becomes authorization. Pagination proxy is path-specific and validates only approved params; private data remain no-store and outside service-worker caches.

Validation: actual PostgreSQL tenant/role/revoke/race/idempotency/immutable-version/deferred-FK tests; exact declared quantities and unknown nutrients/allergens/yield; immutable originalCC0→private edit lineage; separately confirmed demo and unchanged real targets; mobile390/desktop1440 create/edit/history/reload/demo E2E;83API/16E2E regressions, migration/build/Docker/populated restore/privacy, independent nutrition/licensing/security/review and exact-head CI before merge. Archive/delete, normalization, verified nutrition, allergy gates, planning and private offline mutations remain later scope.
